# Zerion 3.0 Technical Whitepaper

## Abstract

Zerion is an end-to-end encrypted, peer-to-peer messenger for Android whose online messaging runs over Tor, with no Zerion servers and no accounts. Zerion's protocol stack, ZTP, ZWF, ZPP and ZMM, carries a hybrid post-quantum ratchet (Mode 3-Full) in which every message is protected by a fresh ML-KEM-768 key encapsulation layered over a classical symmetric chain. While a connection is live, traffic is shaped into fixed-size frames sent at a paced, jittered cadence with two constant rates: an active rate while messages flow and a slower idle rate once the connection has carried only cover for a while, so an observer of an established connection cannot distinguish messages from cover traffic or infer message sizes or timing within a rate regime; the regime transitions reveal the coarse onset and end of activity and a rough bound on how much was sent ([§5.2](#52-zpp-paced-cover-traffic)), and the existence and lifetime of connections is outside this property.

Third-party software notices and attribution are recorded in [NOTICE.md](../NOTICE.md).

This document describes the protocol as implemented in 3.0.17, which is unchanged from 3.0.15. Where an earlier release behaves differently, a dated note says so. Since 3.0.4 the vault also hosts optional, self-custodial Bitcoin and Monero wallets, described in [§9](#9-the-encrypted-vault-and-non-custodial-wallets); since 3.0.8 the cover-traffic cadence has an active and an idle rate ([§5.2](#52-zpp-paced-cover-traffic)); since 3.0.9 the pairing key rotates ([§4](#4-identity-and-pairing-key-exchange)). Where the implementation makes a deliberate trade-off or falls short of an idealised design, this document says so plainly (see [§11, Security Properties and Limitations](#11-security-properties-and-limitations)). Every claim in this document is cross-referenced from [`docs/protocol/SECURITY_CLAIMS.md`](protocol/SECURITY_CLAIMS.md), which names the enforcing code and test for each.

## 1. Design goals

- **Post-quantum by default.** The body key of every application frame mixes a fresh ML-KEM-768 shared secret into a symmetric chain seeded from the contact's root key, which pairing establishes with X25519 and ML-KEM-768 together, so recorded message content is not decryptable by a future quantum adversary ("harvest now, decrypt later"). The Tor layer, channel traffic and account transfer use classical cryptography.
- **No Zerion servers, no accounts.** Peers connect directly to each other's Tor hidden services. There is no central relay, directory, or push service.
- **Metadata minimisation.** While a connection is open, fixed-size frames at a paced, jittered cadence make application traffic indistinguishable from cover, hiding message sizes, counts and timing within each rate regime. The cadence idles to a slower constant rate when no messages have flowed recently, so the transition between the active and idle rates reveals the coarse onset and end of activity, and the length of an active period gives a rough bound on how much was sent (§5.2). Connection existence and lifetime are not hidden.
- **Fail closed.** Any authentication or format failure drops the stream rather than degrading to a weaker mode.
- **Forward secrecy and post-compromise security** on the message stream; post-compromise security covers the per-connection ratchet state and, from 3.0.15 between peers that both run it, the contact root key, which the two peers replace with fresh hybrid secrets ([§6.4](#64-contact-root-evolution), [§11](#11-security-properties-and-limitations)).

## 2. Threat model

Zerion aims to protect against:

- A **passive network adversary** observing a peer's Tor traffic: within an established connection it learns neither the content nor which frames carry messages, within the limits listed in [§5.2](#52-zpp-paced-cover-traffic), and Tor conceals the network location of both peers. Connection lifecycle remains observable, and global traffic-confirmation attacks against Tor itself are out of scope (see below).
- An **active network adversary** that can drop, delay, reorder, or inject frames: it cannot forge or alter authenticated content, and any tampering drops the stream.
- A **future quantum adversary** with recorded ciphertext: the post-quantum layer keeps recorded message content confidential. Tor's own layer (which connections were made, and when), channel traffic and account transfers use classical cryptography.
- **Device seizure of a peer** after the fact: forward secrecy means keys taken from the device cannot decrypt the messages in earlier recorded traffic (the stored root key does open the opening cover frames of a recorded connection and lets its holder link recorded streams to the contact); the stored history is protected by the database encryption and the account password, and by disappearing messages where they are used. The post-quantum ratchet heals a connection after a transient compromise of its ratchet state. A copy of the contact root key lets its holder authenticate as either party of that contact pair in later connections; from 3.0.15, between peers that both run it, only until the next root evolution the holder does not take part in ([§6.4](#64-contact-root-evolution)), and otherwise until the two re-pair ([§11](#11-security-properties-and-limitations)).

Out of scope: a fully compromised endpoint (malware with the screen unlocked), traffic-confirmation attacks against Tor itself, and coercion of a user to unlock the device. Zerion applies platform hardening (see [§10](#10-anti-forensics-and-device-hardening)) to raise the cost of device-level attacks but does not claim to defeat a compromised OS.

## 3. System architecture

This document describes the Android client (a separate desktop client for Windows and Linux exists in its own repository; iOS and macOS clients are in development and unreleased). Each device runs an embedded Tor process (through the in-tree wrapper `org.zerionproject.tor`) and publishes a persistent v3 onion service. A contact is reached by dialling its onion address through Tor's SOCKS proxy. Since 3.0.15 Tor opens no TCP listener on the phone: its control listener, its SOCKS listener and the local end of every onion service the app publishes are Unix domain sockets in the app's private directory, which no other app on the device can open. In the shipped release Tor is the only always-on, mandatory transport for online messaging (the inherited Bluetooth, LAN and Internet-TCP plugins were removed): it is the anonymity floor and cannot be disabled while the app is online; Offline mode stops it together with all internet messaging. Of the additional transports below, the mesh is in the release and off by default; I2P is in development builds only since 3.0.12. Since 3.0.17 an installation from GitHub Releases can check once a day, over Tor, for a signed announcement of a newer release (`docs/release-manifest.json` and its signature on the `master` branch of this repository); a notice is shown only when the announcement is signed with the same key as the installed app, the check can be turned off in Settings, and installations from app stores do not make it.

> **Additional transports (shipped in 3.0).** Two additional transports shipped in 3.0; neither weakens the guarantee that online messaging runs over Tor. (1) **I2P**: an opt-in extra, off by default, over an embedded in-process Java router using I2P's streaming library. Since 3.0.12 I2P is a development-build-only dependency and the published release does not contain it. I2P provides end-to-end tunnel anonymity (a peer does not learn your address); the residual is that a network observer can tell you *participate* in I2P, the same class of exposure as using Tor without bridges. The one clearnet bootstrap step (reseed) is routed through Tor's SOCKS proxy and fails closed, so joining I2P does not reveal the device address unless the development-build option for direct reseeding is switched on. It is off by default with Tor mandatory. (2) **Offline mesh**: a **Bluetooth-only** (no Wi-Fi) store-carry-forward transport for scenarios with no internet at all (disasters, blackouts, protests). It carries 1:1 messages and full group chat over the same hybrid post-quantum identities, using async sealed-sender encryption to a recipient's published post-quantum prekey (ML-KEM-768 + X25519 → XSalsa20-Poly1305, inner Ed25519 + ML-DSA-65 signature) flooded across nearby phones, which relay the sealed envelopes without being able to read them or learn the sender. An earlier Wi-Fi Direct radio was **removed entirely** because it leaked the OS device name and a second MAC and connected indiscriminately, so the mesh is pure BLE. The mesh has a deliberately different threat model from Tor/I2P: it hides *content* but not *physical proximity*, so a co-located adversary can tell that a device is transmitting. It is "communicate when there is no internet," not "hide that you are communicating from someone standing next to you." Both transports are documented in full in [ZERION_MESH_AND_I2P.md](ZERION_MESH_AND_I2P.md).

The protocol stack, from the socket up:

- **ZTP** (Zerion Tor Protocol), runs Tor, publishes the onion services (an open one and, for contacts that have completed client authorization, an authorized one; [§5.4](#54-tor-client-authorization)), dials peer onions, accepts inbound connections, and hands each connected socket to the connection handler.
- **ZWF** (Zerion Wire Format), the fixed-size, authenticated framing on each connection.
- **ZPP** (Zerion Pull Protocol), the paced send scheduler that makes real traffic indistinguishable from cover traffic within a live connection.
- **ZMM** (Zerion Message Module), application message records and fragmentation over the frame stream.

Identity, contacts, the message database and the pairing handshake live in the `org.zerionproject.core` packages (component provenance is recorded in [docs/protocol/README.md](protocol/README.md) and [NOTICE.md](../NOTICE.md)); the ratchet and the four protocols above are Zerion's own.

## 4. Identity and pairing (key exchange)

Each account has a **hybrid identity**: an Ed25519 key and an ML-DSA-65 key for signatures, plus X25519 and ML-KEM-768 keys for the pairing handshake (rotated after every contact addition, see below). A hybrid signature is valid only if **both** halves verify. The identity is named by its Ed25519 key alone: the AuthorId covers only that key (a format that names both keys is specified in [docs/wire/AUTHOR_ID_V2.md](wire/AUTHOR_ID_V2.md) but not active, because every peer must parse it first), and the ML-DSA-65 key is learned from the contact and pinned where a protocol records it (in the contact record at pairing, for groups, in channel ids). Forging a signature therefore requires breaking both a classical and a post-quantum primitive only where the ML-DSA-65 key is pinned; channel comment and reaction signatures carry a self-asserted ML-DSA-65 key and rest on Ed25519. From 3.0.15 the safety number two contacts compare covers both keys of each side (version 2), and the screen names the version shown; 3.0.14 and earlier, and iOS, show a version 1 number over the Ed25519 keys only, which never matches a version 2 number. Since 3.0.15 a member signs in a channel with a key derived for that channel from its identity private key, not with the identity key itself ([§8](#8-11-chat-group-chat-channels-and-voice)).

Pairing starts out of band. There are two pairing paths:

**Link pairing (rendezvous over Tor).** The link carries a commitment to the sender's hybrid handshake key. Both sides meet at a rendezvous derived from the link and run the handshake:

1. Both sides exchange hybrid public keys (X25519 + ML-KEM-768). The master key combines a static-static X25519 agreement, an ephemeral-ephemeral X25519 agreement, the two static-ephemeral X25519 agreements (added in handshake minor version 4 for key-compromise impersonation resistance), an ML-KEM-768 encapsulation to the peer's *ephemeral* ML-KEM key and an ML-KEM-768 encapsulation to the peer's *static* ML-KEM key, through a keyed BLAKE2b KDF with domain separation. The pairing secret is therefore confidential against a future quantum adversary.
2. Authentication is hybrid. Each side proves ownership of the master key with a MAC, the result is bound to the out-of-band commitment (so a man-in-the-middle who relays the handshake cannot match it; from 3.0.15 the X25519 rendezvous key the link also carries in clear must be the X25519 half of the committed key, so every field of the link is authenticated), the contact record exchanged afterwards carries an Ed25519 signature and a hybrid Ed25519 + ML-DSA-65 signature, both over a value derived from the master key and both required to verify, and the B.3 proof binds the static ML-KEM key to the Ed25519 identity. Because the master key includes the encapsulation to the committed static ML-KEM key (handshake minor version 3), completing the handshake requires the static ML-KEM private key: a peer that holds the committed public key and its X25519 private half but not its ML-KEM private half, which is the position of a quantum adversary who recovered the X25519 key, cannot pair (`HandshakePqAuthenticationTest`). The handshake records themselves carry no signature; the ML-DSA-65 key signs the contact record exchanged after the handshake, and records later on. **3.0.11 note (2026-09):** the released 3.0.11 speaks handshake minor version 2 and authenticates the pairing classically; a quantum adversary active at pairing time could impersonate a peer there. No impersonation is known to have occurred.
3. The handshake is **downgrade-resistant**: once a contact is paired with the hybrid protocol, a later attempt that offers only the classical protocol is rejected, and a peer that offers a handshake minor version below the post-quantum authenticated one is refused.

**Nearby pairing (QR code or Bluetooth key agreement).** This path is a QR key-agreement protocol (BQP version 5): both sides exchange hybrid public keys bound to the QR commitment, the initiator encapsulates an ML-KEM-768 secret to the peer's key, and the master secret is derived from the X25519 agreement and the ML-KEM secret together, so a nearby-paired contact has a post-quantum root key like a link-paired one (`KeyAgreementProtocol`, `KeyAgreementProtocolEndToEndTest`). **3.0.11 note (2026-09):** the released 3.0.11 speaks BQP version 4, a classical X25519 agreement; its nearby-paired contacts have a classical root key, and their stream identifiers, frame headers before the first ML-KEM contribution and cover bodies are not post-quantum protected, while their application frames still receive the per-message ML-KEM-768 mix of [§6](#6-the-mode-3-full-ratchet).

The handshake output is the per-contact **root key** from which every subsequent connection derives its session state. From 3.0.15 two peers that both run it replace the root with fresh hybrid secrets ([§6.4](#64-contact-root-evolution)); with an older peer, and in 3.0.14 and earlier, it is never rotated or ratcheted ([§11](#11-security-properties-and-limitations)).

**Rotating pairing links.** The public key a pairing link carries is not a permanent identifier: after every successful contact addition the local handshake key pair is rotated, so the next link shared is new. A pairing that is still in flight is unaffected, because each pending pairing is bound at creation to the key pair that was current when it was created and completes with that pair. A link captured from an earlier exchange therefore stops being answerable once the pairings created under it have resolved or expired, and two links shared at different times do not reveal a common key. This property is scoped to the pairing identifier: contacts who complete pairing still learn the durable identity keys described above, which are shared across all of a user's contacts. From 3.0.15 a pending invitation expires two days after it was created, whatever happens in between (earlier releases extended it by two days at every restart), and a contact's link entered after the user's own link has changed adds nothing and asks the user to share the new link instead; the link compared is the one the user last shared (copied, shared or shown as a QR code), remembered for two days across visits to the screen. Re-adding a contact one already has, by a new link exchange, is allowed from 3.0.15 and replaces that contact's connection keys in place while keeping the conversation ([§6.4](#64-contact-root-evolution)).

**Verification.** From 3.0.15 a contact is shown as verified only after the user compares the safety numbers on both devices and marks it so in the chat settings, or scanned the contact's code from their screen in person (nearby pairing, or the QR exchange of the add-contact screen), which authenticates the key the same way. A link received any other way does not mark a contact verified: a link passed through a channel an attacker controls could have been replaced. 3.0.14 and earlier stored every link-paired contact as verified and offered no way to verify by hand; the update resets those contacts to unverified, including ones that were scanned in person before 3.0.15. Media can be sent to a contact the user added directly or verified, and not to an unverified contact that only an introduction vouches for, as before. Safety numbers and fingerprints are shown the same way everywhere (Settings, a contact's details, a group member's key): version 2 covers both identity keys and appears once both devices know each other's ML-DSA key, which two 3.0.15 devices exchange inside their next connection under an Ed25519 signature of the author key; version 1 covers the Ed25519 key alone and is always shown next to it, so a contact whose app only computes version 1 can still be compared.

## 5. Transport stack: ZTP, ZWF, ZPP, ZMM

### 5.1 ZWF, fixed-size authenticated frames

Every frame on the wire is exactly **4096 bytes** (`FRAME_LENGTH`), regardless of payload. Short payloads are zero-padded; larger application messages are fragmented across frames (by ZMM). Because a real frame and a cover frame are byte-for-byte the same size, an observer cannot tell them apart or infer message length.

A connection begins with a 16-byte **stream tag** and an encrypted **stream header** (`[wire version:2][streamId:8]`, 50 bytes on the wire including the 24-byte nonce and 16-byte MAC). Thereafter each 4096-byte frame is three independently-authenticated AEAD segments:

- **Segment 0, frame header** (4 bytes plaintext + 16-byte MAC): the payload length and padding length, encrypted under the classical message key.
- **Segment 1, Mode 3-Full header**: the sender's advertised ML-KEM public key, the ML-KEM ciphertext, a key-pair id, and a 32-byte field once meant for an X25519 ratchet key (unused, and all zero from 3.0.15, see [§6.3](#63-the-classical-dh-ratchet-is-inert-by-design)), encrypted under the classical message key, so the post-quantum material is authenticated *before* it is used (see [§6](#6-the-mode-3-full-ratchet)).
- **Segment 2, body**: the application payload plus padding, encrypted under the **hybrid** body key.

The **stream id** is a persistent, strictly-monotonic 64-bit counter that is not reused across reconnects, restarts or key rotations in normal operation (a database restored from backup can hand back a used id). It is bound into the AEAD nonce and, together with the random stream-header nonce, seeds the ratchet chain, so a reused id does not repeat a (key, nonce) pair ([§6.1](#61-per-message-keys)) but does repeat the stream tag; the counter is persisted before any frame is sent. On receive, a stream id is validated against a sliding replay/reorder window of 256; within a stream, frames are strictly in order and any gap drops the stream.

### 5.2 ZPP, paced cover traffic

While a connection is live, the send side emits one frame per iteration through a scheduler: the next queued record if there is one, or a **cover frame** if the queue is empty. Pacing is self-paced rather than slotted: after each frame the sender waits a uniformly jittered delay (±1/3) around the current base interval, so the exact-interval fingerprint is removed and a stall lengthens the cadence instead of producing a catch-up burst. Since 3.0.8 there are two constant base intervals (`ZppPacingPolicy`): **750 ms** while application records flowed in the last two minutes or are queued (the active rate), and **4 s** afterwards (the idle rate), the same on every network type. A frame is never sent closer than the active spacing, so the onset of activity cannot burst. Cover and real frames are indistinguishable on the wire within a rate: an observer of an established connection cannot tell a message from cover, or learn message sizes or counts. What the observer can learn from the switch between the two rates is the coarse onset and end of activity (to within the two-minute idle threshold), not what was sent; because the active rate lasts while records are queued, the length of an active period gives a rough bound on how much was sent (a frame carries at most 1698 bytes of payload). In 3.0.14 and earlier, records this side queues in reply to the peer (acknowledgements, requests, resends the peer asked for) also select the active rate, so a peer that keeps sending can keep this side at the active rate; from 3.0.15 only content this side produced selects it, and a reply the peer provoked goes out at the current rate. This property is per live connection; it does not conceal when connections open or close, reconnects, or the number of live sessions, and a queued message dials the contact at once, so the opening of a connection can coincide with a send. Calls and channel requests do not use this pacing.

Because cover frames flow continuously, they also bootstrap the ratchet: the two peers exchange their ML-KEM public keys within the first slot or two of a connection, before any human-typed message is sent.

### 5.3 ZMM, records and fragmentation

Application data (private messages, group records, voice-call signalling, receipts and acknowledgements) is carried as sync records in one ZMM record type; from 3.0.15 a second type carries the root evolution of [§6.4](#64-contact-root-evolution), which the transport handles itself and older peers drop as unknown. Records larger than one frame's payload capacity are fragmented and reassembled, up to 1 MiB; from 3.0.15 the sender never queues a larger record, which the receiver would drop and the sender would otherwise offer again forever. A cover frame carries a distinguished cover record that the receiver drops. Channel traffic does not use ZMM ([§8](#8-11-chat-group-chat-channels-and-voice)). Received application messages are deduplicated by message id against the (encrypted) database while the message is stored; a message that has since been removed from the database (for example by disappearing-message expiry) can be accepted again if the same contact re-sends it.

### 5.4 Tor client authorization

Every contact pair whose apps both advertise support (transport property `onion3auth`) moves from the open onion service to a second, client-authorized onion service. Each side generates a random X25519 dialing key pair for the other, publishes the other's public half as a client-authorization entry on its own authorized service and hands its private half to Tor as a non-permanent credential for the other's service. Keys are directional and per contact: the private half exists only on the device that dials with it, and no two contacts share a key. An address holder without a credential cannot decrypt the descriptor layer that carries the introduction points and cannot connect; Tor reports a missing client authorization at the SOCKS layer.

Activation runs over a dedicated per-contact sync client with six records (offer, ready, probe success, commit, rotate, rotate acknowledgement). A pair commits only after both sides have proven the authorized path: the designated dialer must have reached the peer's authorized address, and the other side must have received a recognised connection from the peer through its authorized listener. After commit the pair is in the persisted state `AUTH_REQUIRED`: the authorized address is the only dial target, a committed contact arriving over the open service is refused, and there is no fallback to the open address; a device that loses its credential state is paired again rather than downgraded. Removing a contact revokes their key at once, deletes the old authorized service and publishes a new one for the remaining contacts, which are told the new address; a normal rotation keeps the old address until every contact has acknowledged the new one. Tor restarts are covered by re-feeding the service and the credentials from the database before any dial. The open service stays published for contacts whose app does not yet support client authorization; since 3.0.15 removing a contact also rotates the open address: a rotation is owed until it runs, one already under way is abandoned for a fresh address the removed contact never saw, and the address the removed contact knew is retired once the remaining contacts have moved, within 48 hours at most and at once when no contact is left. Design, state machine, wire format and the Tor control behaviour confirmed on the shipped Tor 0.4.9.12 and on 0.4.9.13 are in [docs/protocol/ONION_CLIENT_AUTH.md](protocol/ONION_CLIENT_AUTH.md). **3.0.11 note (2026-09):** 3.0.11 does not have client authorization; it shipped in 3.0.12.

## 6. The Mode 3-Full ratchet

Mode 3-Full is Zerion 3.0's single message ratchet. It combines a classical symmetric chain (for forward secrecy) with a per-message post-quantum key encapsulation (for post-compromise security and quantum resistance).

### 6.1 Per-message keys

For each frame the sender:

1. Advances a **classical chain key** with a keyed BLAKE2b KDF to produce a per-message *classical key*. The chain is seeded once per connection from `(rootKey, streamId, streamHeaderNonce)`, where `streamHeaderNonce` is a fresh random value carried in the authenticated stream header, and is one-way, giving **forward secrecy**: a compromised chain key cannot recover earlier message keys. Salting the seed with the per-stream header nonce means that even a database restored from backup, which could hand back an already-used `streamId`, derives a different chain and never repeats a (key, nonce) pair.
2. Performs a **fresh ML-KEM-768 encapsulation** to the peer's current ML-KEM public key, yielding a ciphertext (sent in the frame's Mode 3-Full header) and a shared secret.
3. Derives the **hybrid body key** as `BLAKE2b-KDF(classical key, ML-KEM shared secret)`. The frame body is encrypted under this hybrid key, so the body stays confidential as long as *either* the classical chain *or* ML-KEM-768 is unbroken.
4. Folds the ML-KEM shared secret back into the chain key for the next message. Once a post-quantum secret has been absorbed, the chain can no longer be recomputed from `rootKey` alone, so forward secrecy and healing extend to the symmetric chain itself rather than resting only on the per-message hybrid body key.

The receiver mirrors this: it authenticates the Mode 3-Full header, decapsulates with the matching private key (looked up by key-pair id), and derives the same hybrid key.

**Post-quantum coverage is per message.** The only exception is the very first frame a side sends before it has learned the peer's ML-KEM public key: that frame carries an all-zero "sentinel" ciphertext and is classical-only. Because the cover traffic exchanges public keys within the first frame or two, this sentinel only ever applies to an opening cover frame and never to a user message, and once a direction has accepted a real ML-KEM ciphertext the receiver rejects any later sentinel on that direction. The rule that application data travels only in frames with an ML-KEM secret is enforced by the sender, and from 3.0.15 by the receiver as well, which drops every record but cover that arrives in a sentinel frame. In 3.0.14 and earlier the receiver would still deliver records from a sentinel frame before its latch was set, so a modified sender, or anyone holding the root key, could deliver data under root-derived keys only.

### 6.2 Key rotation and post-compromise security

Post-compromise security ("healing" after a transient key compromise) comes from **rotating the ML-KEM key pair**. A sender generates a new ML-KEM key pair every `MODE3_FULL_SEND_ROTATION_INTERVAL` = **16 messages** and advertises the new public key; the peer then encapsulates to a key whose private half a past attacker does not hold, locking the attacker out. Up to **32** recent private key pairs are retained per connection so that in-flight frames encapsulated to a just-superseded key still decrypt; older ones are pruned and zeroised once the peer uses a newer key, and rotation pauses while 32 are retained. That happens only when the peer has not used a newer key for about 512 of this side's sends; the pause is deliberate, because evicting a key pair the peer's frames still in flight may use would break the connection, so in that one case rotation waits for the peer. **Each connection starts a fresh Mode 3-Full state** from the contact's root key, so ML-KEM keys do not carry over between connections; healing of the root key itself comes from root evolution ([§6.4](#64-contact-root-evolution)), not from this ratchet. Within a connection, healing extends to the symmetric chain itself: each message's ML-KEM shared secret is absorbed into the chain key (§6.1), so after an exchange whose lattice secret a past attacker cannot decapsulate, the chain state is beyond that attacker's reach even if they had captured an earlier chain key.

### 6.3 The classical DH ratchet is inert (by design)

The Mode 3-Full frame header also carries a 32-byte field for an X25519 public key, a vestige of the classical Double Ratchet inherited from the upstream design. **In the 3.0 build this classical DH ratchet does not run**: the field drives no ratchet step and no Android receiver parses it. Up to 3.0.14 it carried a fixed X25519 key whose private half the database kept; from 3.0.15 it is sent as zeros, the dead ratchet code and its stored keys are removed, and the field stays only so the frame layout is the one every peer parses. The classical layer therefore contributes **forward secrecy** through its one-way chain, but **not** post-compromise security within a connection.

This is a deliberate deferral: the post-quantum ML-KEM ratchet already provides post-compromise security, so the classical DH ratchet was judged redundant and left unwired rather than maintained. The consequence, that post-compromise security rests entirely on the post-quantum layer, with no independent classical backstop, is stated honestly in [§11](#11-security-properties-and-limitations). Zerion does not claim a working classical Double Ratchet.

### 6.4 Contact root evolution

From 3.0.15, at the start of a connection between two peers that both run it, at most once every ten minutes per contact, the two peers replace the contact root key: inside the authenticated connection they exchange fresh ephemeral X25519 keys and an ML-KEM-768 encapsulation, derive the next root from a subkey of the current root, both fresh secrets and the transcript, prove to each other that they hold it, and delete the old root. Each side stores the new root before it proves possession and uses it for a connection only after the peer proved possession, no side ever drops a root the peer may still hold, the greeting that opens the exchange is built at the moment it leaves, and the side that dials alternates between the new root and the old one while its dials fail, so a connection cut at any step, two connections running at once, a stale greeting from a parallel connection, a replayed greeting from a holder of a copied root or a write lost on one side never leaves the pair unable to connect; the side that accepts a connection answers under the root the dialler chose, and answers at most three offers per contact per ten minutes. Afterwards a copy of an older root authenticates in neither direction. If the two sides' roots have diverged for good (an older backup restored on one side after the other side had moved on for more than the seven-day pause), the dialling side notices after six dials that were accepted but never authenticated and shows that the connection keys are out of sync; the other side only sees the contact offline. Re-adding the contact by a new link exchange replaces the keys on both devices in place and keeps the conversation. Nothing re-keys two diverged devices automatically: anyone holding a copy of the database holds every secret such a mechanism could use, so it would let the copier back in. Each root above the pairing root is used only through separate subkeys for the transport keys, the next root and the proofs. Peers that do not run it (Android 3.0.14 and earlier, iOS) drop its records as an unknown type and keep the pairing root, which both sides also keep as the voice-memo wrap key. The protocol, its records and its interruption cases are in [docs/protocol/ZWF-ROOT-EVOLUTION.md](protocol/ZWF-ROOT-EVOLUTION.md).

A backup or a transferred copy of the account holds the roots of the moment it was made, so it reaches a contact only until that contact's root evolves past it. Making a copy therefore pauses new evolutions on the device for seven days, and no root changes at all while the copy is written, which keeps the move to a new phone working; once the new phone has connected to a contact, the old phone and older copies can no longer reach that contact. The export and import screens say so, and a contact restored out of sync is repaired by re-adding it.

## 7. Authenticated encryption and nonces

The AEAD is **XSalsa20-Poly1305** (the NaCl `secretbox` construction): a 24-byte nonce, a 256-bit key, and a 128-bit Poly1305 tag verified in constant time before any plaintext is released.

The 24-byte nonce is constructed from `streamId`, the 64-bit frame number, the segment index (0/1/2), and a bit identifying which peer originated the stream. This guarantees that no `(key, nonce)` pair repeats:

- The **segment index** separates the three segments within a frame even when the frame-header and body happen to use the same key (the sentinel case), so their keystreams are disjoint.
- The **frame number** advances every frame and the classical message key advances every message, so no nonce recurs across frames of a stream.
- The **originator bit**, together with role-separated key derivation, keeps the two directions of a connection disjoint.

Buffers that Zerion controls, such as message keys and KEM shared secrets, are zeroised after use where the code does so. From 3.0.15 replaced chain keys are zeroised frame by frame, and when a connection ends so are its ML-KEM decapsulation keys, its stream chain keys, its direction, tag and stream-header keys and the copies of the root keys loaded for it. Not everything is cleared: the cryptographic library's own key objects (such as the ML-KEM private-key parameters it builds for each decapsulation) are left to the garbage collector, and the runtime and libraries may keep copies.

## 8. 1:1 chat, group chat, channels and voice

- **1:1 chat.** Every private conversation runs the Mode 3-Full ratchet described above over a dedicated pair of ZWF streams (one per direction) on a direct Tor connection between the two peers. Messages, read receipts and typing state are ZMM records; attachments are fragmented across frames. There is no server copy of any message. Since 3.0.15 a conversation also carries PDF and text documents, from the phone or the vault, in the chunked attachment format: a document is sent unchanged under the type its content matches (unlike photos and video, its metadata is not removed), is shown as a document and opens in another app only through the external viewer checks; a contact on 3.0.14 sees it as an image that cannot be shown and can open it from the media overview, and a contact whose app cannot receive chunked attachments is refused with a message.
- **Group chat (GroupTr).** Groups are serverless and have no shared group key and no group ratchet: the sender of a post sends a separately signed copy over its existing pairwise 1:1 Mode 3-Full connection to every member who is also its contact (other members do not forward posts, so a member who is not the sender's contact does not receive that post). Every copy is therefore protected per-message by ML-KEM-768 exactly as a private chat is, and nothing group-related is in the clear on the wire. Group membership is authoritative from the group creator: each membership change (add or remove) is carried in a record signed with the creator's hybrid (Ed25519 + ML-DSA-65) identity and is rejected unless that signature verifies, and each change advances an epoch counter that members use to reject stale membership state. A member's own leaving takes it out of the member list without moving the epoch, and the creator confirms it with its own removal and epoch commit (from 3.0.15; in a group whose creator runs an earlier version a leaving still moves the epoch by one). The group's disappearing timer is set by the creator and carried to the members in a signed settings record; each device applies it to the posts it sends and receives (from 3.0.15, for members on that version). Known limitations of the current Android implementation: leave, dissolve, role-change and snapshot records are not bound to the contact that delivers them, so a validly signed older record relayed by any contact is accepted when its epoch is higher than the local one. Removal is enforced by the remaining members no longer sending to the excluded member and no longer accepting its posts, not by re-keying a shared secret (there is none to re-key); forward secrecy against a removed member therefore rests on the honest members' devices applying the removal, and a member who chose to keep sending to an excluded party could still reach it. Group records travel as sync records inside ZWF frames.
- **Channels** are single-publisher, many-subscriber broadcast (announcements, feeds). The publisher signs each post with the channel's hybrid key and serves posts from a dedicated channel onion; subscribers pull over Tor and verify the signature chain, so a subscriber needs no trust in any third party, and a subscriber who only reads reveals nothing to the publisher beyond a connecting Tor circuit (and, for a private channel, possession of the shared capability). Channel requests and replies are length-prefixed messages on a direct Tor connection to the channel's onion service; they do not use ZWF, ZPP or the Mode 3-Full ratchet, and their confidentiality is classical: public channel posts are protected only by the Tor onion-service encryption in transit, private channel post bodies are also encrypted with AES-256-GCM under a channel content key, and attachment blobs are AES-256-GCM encrypted under per-attachment keys. Posts, comments and reactions are content-addressed and tamper-evident. Since 3.0.15: every post carries a random salt that its signature and, in a private channel, its body nonce cover, and its signature covers every attachment field including the per-attachment key; a post that expires or is deleted never gives its sequence number back, a publisher restored from a backup jumps its numbers ahead instead of repeating them, and its subscribers find it again at an earlier onion; subscribers fetch only the reactions and comments that changed, and pull each channel on its own randomly jittered schedule; a member reacts, comments and applies with a key of that channel only, derived from its identity private key, so its activity in one channel cannot be linked to its identity or to its activity in another; anonymous keys can no longer erase or crowd out what the subscribers the owner marked as trusted wrote; editors can post, within a bounded number of posts and bytes, and cannot delete; each channel moves to a fresh onion every few weeks, and at once when a private channel's invite link is rotated; and deleting a channel deletes everything kept for it, its onion serving only the signed tombstone for 14 days. Clients up to 3.0.14 cannot read posts made from 3.0.15 on and are refused them without storing anything. Details and current limitations are in [docs/wire/CHANNELS_WIRE_PROTOCOL.md](wire/CHANNELS_WIRE_PROTOCOL.md).
- **Calls and the app lock.** Since 3.0.15 an incoming call shown over the phone's lock screen, while the app is locked, or before a disguise's code has been entered, is a neutral ringing screen: no name, no app label, no call type. Answering, from the screen or from the notification, first asks for the phone's unlock and then for the app's unlock; cancelling either leaves the call ringing, and declining needs neither. The call screen counts as an app screen from the app unlock on, so the app lock's timer starts again when the call screen closes. The call screen has a task of its own and stays out of the recent apps, so no other screen of the app, and no other app, can close it.
- **Voice and video calls** are peer-to-peer over Tor: uncompressed 16 kHz mono PCM audio (256 kbit/s) in fixed 20 ms / 640-byte frames and H.264 video in padded frames, encrypted with AES-256-GCM under a call key negotiated over the authenticated messaging channel. Since 3.0.15, when both phones run that version, the offer and the answer also carry X25519 public keys, and the media keys mix their agreement with the call key and the call id: the private keys never leave the phones and are wiped once used, so the call cannot be decrypted later from what the signalling carried or the database kept; the audio keys stay the same across reconnects, every audio frame seals its direction and sequence number, and the caller only dials the endpoint derived from the call key. A call with a phone of an earlier version, or with the iOS app, keeps the earlier key schedule. The fixed audio frame size and cadence avoid leaking speech patterns through packet timing, and there is no codec-dependent frame size to leak them either (`VideoSessionKeyDerivationTest`). **3.0.11 note (2026-09):** in the released 3.0.11 the derivation of the per-call keys has a defect (the derived key material is zeroed before use) and the video nonce can repeat when video is stopped and restarted within one call; both are corrected in 3.0.12. No exploitation is known.

## 9. The encrypted vault and non-custodial wallets

The vault is an on-device encrypted store for passwords, secure notes, documents and images, separate from messaging and protected by its **own** password.

- **Key derivation.** The vault password is stretched with **Argon2id** (256 MiB, 3 iterations; on a device that cannot spare 256 MiB, 128 MiB with 6 iterations, which the vault settings then say). Since 3.0.15 the vault has a random master key, wrapped under `HKDF-SHA256(HMAC_keystore(Argon2id(password)) XOR unwrap(secret))`: the HMAC is computed by a key that never leaves the Android Keystore (in **StrongBox** where the device has it), on every password guess, and the random secret is wrapped by a second keystore key. Someone who can use the keystore once therefore still cannot test passwords offline, and neither the password alone nor a copied data directory alone opens the vault. A password change draws a new master key, wraps every item key again under it, and moves to new keystore keys, deleting the old ones, so an earlier copy of the vault no longer opens with the old password. A vault of an earlier version (master key `HKDF-SHA256(Argon2id(password) XOR unwrap(secret))`, often derived with 128 MiB and 2 iterations) is moved to this form at its next unlock, its items unchanged. The keystore keys do not require an unlocked device, so removing the screen lock does not lose the vault.
- **Encryption at rest.** Vault items (`PasswordEntry`, secure notes, documents, gallery media) are encrypted with authenticated encryption through a secure file-I/O layer; nothing in the vault is written in the clear.
- **No recovery.** There is no password-reset or recovery path, a forgotten vault password means the data is unrecoverable by design, so there is no backdoor to coerce.
- **Locks when idle** and on app lock (since 3.0.15, the app lock locks the vault whatever the vault's own auto-lock setting). A PDF is rendered from an anonymous memory file on Android 11 and later; on Android 10 it is read from a cache file that is unlinked before rendering starts, so it has no name while it is shown and is gone when the viewer closes or the process dies, but its blocks may have reached flash. A received chat video is played from memory and never written to storage.
- **Clipboard.** A password or user name copied from the vault is marked sensitive, and is cleared whenever the vault locks (leaving the vault, its auto-lock, the app lock), on sign-out and on panic; the vault's "clear clipboard after" setting adds a timed clear on top. On sign-out or panic while another app has the focus, Android does not let Zerion tell its copy from another app's, so the clipboard is cleared.
- **Per profile.** From 3.0.15 each profile on the device has a vault of its own, in that profile's directory and under an Android Keystore key of its own; another profile's session does not see it, and deleting a profile erases it. A vault from an earlier version, which all profiles shared, moves into the profile that owns it: at once on a device with one profile, otherwise into the profile that next unlocks it with its password (until then every profile still sees it, as before). The wallet files follow their vault.
- **Screen protection.** Vault screens are `FLAG_SECURE` (excluded from screenshots and the recents thumbnail) while the vault's hide-content setting is on, which is the default; with it off they follow the app-wide screenshot setting, also on by default. Every text field in the app, those in dialogs and those added after a screen opened included, asks the keyboard not to learn from it or suggest (a request a keyboard can ignore). From 3.0.15 a password field's characters reach only accessibility tools such as screen readers on Android 14 and later, and no accessibility service at all below Android 14, where every service receives one bullet per character. Markdown notes are shown as styled text, so no web engine runs and none leaves a data directory. An encrypted export (`.zenc`) is written where the user picks, under a neutral suggested name; the item's name travels only inside the encrypted file.

### 9.1 Non-custodial Bitcoin and Monero wallets

Zerion 3.0.4 adds optional non-custodial Bitcoin and Monero wallets that live inside the vault. They are **self-custodial and device-local**: the wallet seed is generated on the device, sealed as a vault item, and never leaves it. There is no custodian, no account, and no server that can move or freeze the funds. The Electrum servers the Bitcoin wallet queries (over Tor) learn its addresses and balance. A wallet is reached only after the vault is unlocked, and each wallet carries its **own** password, distinct from the vault master password.

- **Seed sealing and spend-authority derivation.** Each wallet's seed is stored as a vault item under authenticated encryption. Obtaining spend authority requires the wallet password stretched with **Argon2id** (memory-hard) combined with an Android keystore factor, so decrypting the vault tier alone never yields spending power.
- **Bitcoin.** A BIP84 native-SegWit wallet (bitcoinj, mainnet): a fresh address per receive, fresh change addresses, coin control with per-output freezing and labels, and a cluster-aware privacy analyser. A send is authorised by reviewing the exact transaction; the reviewed plan is fingerprinted, the credential is re-checked, and only that same plan is signed and broadcast, so what the user reviews is what is broadcast (per-input value is bound by the SegWit signature, so a tampered input voids the signature rather than moving funds).
- **Monero.** A wallet built on Monero's own `wallet2` (pinned upstream source, built reproducibly, see below). At runtime it runs as a **spend-keyless, view-only** wallet, so day-to-day balance and history never bring the spend key into memory. For a send, the spend-capable wallet is opened with a key derived from the wallet password (Argon2id) and closed when the send ends, is cancelled, waits at review for three minutes or the vault locks. Receiving uses fresh subaddresses, never the primary address.
- **Tor by default.** By default all wallet network traffic (the Electrum client for Bitcoin, Monero nodes, broadcast, and price lookups) is carried over Tor through the local SOCKS proxy, with distinct stream isolation per wallet and per purpose, and no silent fallback to a direct connection. A non-Tor path exists only as an explicit, opt-in choice behind a warning (a direct node) or as a local node the user adds. No Offline-mode check covers these non-Tor wallet paths.
- **Transaction-time authorisation.** Spending, revealing a seed, deleting or rescanning a wallet each require the wallet password at the moment of the action and are re-validated against the live lock state, so a screen left open cannot authorise a spend after the vault has locked. The displayed spendable balance never counts funds already committed to an unconfirmed send.
- **No forensic residue.** Wallet screens are `FLAG_SECURE` by default (see the vault's screen protection above), the production build writes no logs from the wallet code, and the secret buffers Zerion controls (passwords, seeds, derived keys) are zeroised after use where the code does so; the runtime and native libraries may keep copies.

**Reproducible native provenance.** The wallets rely on native libraries (Monero's `wallet2`, and Argon2 for key derivation). These are built from **pinned upstream source** inside a pinned container, never downloaded as opaque prebuilt binaries: the Monero commit and every dependency archive are hash-pinned and verified at build time, and each shipped library's per-ABI SHA-256 is published so that anyone can reproduce the build and confirm the bytes. The libraries ship inside the signed application package.

**Review.** The wallet foundation (the vault and its cryptography, the Bitcoin and Monero wallets, and the native boundary) has been through extensive internal security and code review in several separate adversarial passes, and through two independent focused security reviews (the Monero wallet native integration and the Bitcoin wallet with the dormant PayJoin component), with the findings addressed in the shipping code. The review history is in `SECURITY.md`.

## 10. Anti-forensics and device hardening

Zerion is designed to resist not only the network adversary but also examination of a **seized device**.

- **Duress and panic.** Zerion registers as a Guardian Project **panic responder**: a trusted panic trigger (for example from Ripple) locks the app immediately, and can be configured to wipe the account. The trigger is authenticated by signature pinning so a hostile app cannot spoof it. Since 3.0.15 the panic settings, including which panic app is connected, are kept only in the encrypted settings.
- **Erase after failed passwords.** The opt-in erase after six wrong passwords in a row applies to every prompt for the account password: sign-in, the password gates in the settings, the current password of a password change and the hardened-mode block screen, which also honour the duress password. Since 3.0.15 an attempt is counted, durably, before the password is checked, so stopping the app during the check does not save an attempt; failures are forgotten only by a successful sign-in, not after a quiet day; and the account manager records the erase before it reports the refusal, so a process that dies part way completes the erase at its next start. A start that finds no account key but data left over (a damaged key file, for example) deletes nothing and asks the user; data is erased only when an erase was requested, by the user, a panic, the duress password or the erase policy. Key files that are damaged never lead to an erase.
- **One form of every password.** Since 3.0.15 the account password, every profile's password, the duress password, the vault password and backup passphrases are all used in one normal form (Unicode NFC, without invisible and input-dependent characters), whichever screen they are typed on. A key an earlier version stored under the text as typed still opens and is stored again in the normal form.
- **Decoy launcher.** The app can present as a working **calculator** (or other innocuous app) via activity-aliases; the real app is reached only through a hidden entry, which hides Zerion from a casual look at the launcher; the package remains visible in the system's app list and to forensic examination. Message notifications are content-free and can be hidden so the lock screen does not reveal the app. Since 3.0.15, while a disguise is active, notifications carry the disguise's name, a neutral icon and neutral text and open the app through the disguised entry, other apps no longer offer Zerion for links or shared text, and an incoming call names nobody until the disguise's code has been entered; the system's app settings still show the app's real name.
- **Hardened mode.** Three opt-in protections, off by default: refuse to start on a device whose boot state or system image fails verification, refuse to start under a debugger, root or hooking framework, and sign out or wipe when USB debugging or file transfer is switched on.
- **No forensic residue.** Zerion's own code contains **no logging calls**, enforced by a build-time check; Tor runs without a log and the Monero library's logging is silenced, but native libraries and the operating system can still write to logcat. Message content never appears in notifications or on the lock screen; screenshots and the recents thumbnail are blocked on content screens by default (`FLAG_SECURE`, a user setting that is on by default); photos and videos are re-encoded or remuxed to strip EXIF and other metadata before sending (in groups and channels from 3.0.15), while other file types are sent unchanged; and decrypted media/temporary files are overwritten before deletion, not just unlinked (a logical erasure, see Storage).
- **Memory hygiene.** Buffers that Zerion controls, such as message keys, shared secrets and derived keys, are zeroised after use where the code does so, to shorten their lifetime in RAM; not every key is cleared (see [§7](#7-authenticated-encryption-and-nonces)), and the runtime and libraries may keep copies.
- **Storage.** The message database is **SQLCipher** (AES-256, schema version 72) with `cipher_memory_security` and `secure_delete` enabled; its key is derived from the account password with Argon2id (64 to 256 MiB, adapted to the device, 3 iterations) combined with a device-bound keystore HMAC factor. Since 3.0.15 that keystore key does not require an unlocked device (earlier versions required one on StrongBox devices, and removing the screen lock then made every profile unopenable; such a key is replaced at the profile's next sign-in), and every key file is bound to a keystore key of its own, which is deleted once no key file uses it: after a password change a copy of the old key file no longer opens with the old password. The database key itself is not changed by a password change, so a backup file made earlier keeps opening the database with its own passphrase. Preferences use the in-tree Keystore-backed `ZerionEncryptedPrefs` or the SQLCipher-backed settings store, never plaintext `SharedPreferences`. Overwrite-before-delete is a logical erasure: flash storage below the file system may retain copies.
- **Platform.** Minimum Android 10 (API 29), targets Android 16 (API 36); native libraries are 16 KB-page aligned; tapjacking and overlay-window defences are applied to sensitive screens.

## 11. Security properties and limitations

**Properties provided:**

- **Confidentiality and integrity** end-to-end, with post-quantum protection on every one-to-one and group message; channels and account transfer are classical.
- **Forward secrecy**: the one-way classical chain and fresh per-connection ratchet state mean a compromised current chain or ML-KEM key does not expose past messages of that connection; stored history is protected by the database encryption, not by forward secrecy.
- **Post-compromise security** of the ratchet state: healing via ML-KEM key rotation (every 16 own sends) and fresh ratchet state on every reconnection. From 3.0.15 the contact root key heals as well, at the next root evolution between two peers that both run it ([§6.4](#64-contact-root-evolution)); see the limitations.
- **Mutual authentication**: hybrid authentication at pairing (ownership MACs bound to the out-of-band commitment, the encapsulation to the committed static ML-KEM key, Ed25519 contact-record signature and B.3 proof) and per-frame AEAD thereafter; the post-quantum public key and ciphertext are authenticated before use. In the released 3.0.11 the pairing authentication is classical ([§4](#4-identity-and-pairing-key-exchange)).
- **Metadata resistance within a live connection**: fixed 4096-byte frames at a paced, cover-filled cadence over Tor hide content, size and count; timing is hidden within each of the two rates, and the switch between rates reveals the coarse onset and end of activity, with the limits listed in [§5.2](#52-zpp-paced-cover-traffic) (active-period length, replies the peer provokes, connection onset).
- **Replay and reorder protection**: strictly-monotonic persistent stream ids, a 256-wide receive window, strict in-order framing per stream, and message-id deduplication at the database layer.
- **Fail-closed**: any authentication or format failure drops the stream.

**Honest limitations:**

- **Post-compromise security within a connection is post-quantum-only.** Because the classical DH ratchet is inert ([§6.3](#63-the-classical-dh-ratchet-is-inert-by-design)), there is no independent classical healing mechanism inside a connection; a hypothetical implementation flaw in the ML-KEM ratchet would not be caught by a classical backstop. Root evolution ([§6.4](#64-contact-root-evolution)) mixes fresh X25519 and ML-KEM-768 secrets. Wiring an independent classical DH ratchet is possible future defence-in-depth.
- **Pairing authentication in the released 3.0.11 is classical** ([§4](#4-identity-and-pairing-key-exchange)), and its nearby pairing is classical throughout; there, post-quantum protection at pairing is confidentiality (harvest-now-decrypt-later resistance), not authentication. Since 3.0.12 both paths are authenticated with the static ML-KEM key as well.
- **Opt-ins that bypass Tor.** A direct wallet node (when selected) learns the device address, and a local wallet node the user adds is reached directly; neither path has an Offline-mode check. In development builds only, I2P participation (when enabled) is visible to the user's network. All are off by default, and the direct node and I2P are behind a warning.
- **Call media** in the released 3.0.11 is protected by the Tor onion-service layer only ([§8](#8-11-chat-group-chat-channels-and-voice)); since 3.0.12 it is encrypted end to end as designed.
- **Healing of the contact root key is limited.** The root seeds every connection with that contact, so anyone who copies it (from an unlocked device, a backup file and its passphrase, or a memory image) can authenticate as either party of that contact pair in later connections. From 3.0.15 that lasts until the next root evolution the copier does not take part in; a copier who holds the current root and is active during the evolution keeps its position, as with any post-compromise scheme. With a peer that does not run root evolution (Android 3.0.14 and earlier, iOS), and in 3.0.14 and earlier, the root is never replaced and a copy works until the two re-pair (claims matrix, compromise model). An older backup restored after a contact's root has evolved cannot reach that contact until the two pair again ([§6.4](#64-contact-root-evolution)).
- **Healing granularity** of the ratchet state is one ML-KEM rotation (16 own sends) or one reconnection, not strictly per message.
- **Post-restart stream replay** at the wire layer is refused: the persisted receive high-water mark acts as a startup floor (`ZwfStreamCounter`), so a restart does not reopen the 256-id window; the database message-id deduplication remains a second layer.
- **Group messaging has no shared group ratchet.** As described in [§8](#8-11-chat-group-chat-channels-and-voice), group content rides the members' pairwise post-quantum ratchets and group membership is authenticated by the creator's hybrid signature, but there is no group-wide key. Removing a member is enforced by the remaining members no longer relaying to them, not by re-keying a shared secret, so forward secrecy against a removed member depends on the honest members and a member who kept relaying could still reach an excluded party. A group is only as confidential as its members choose to keep it.
- **Channels: reading does not identify you to the publisher; reacting and commenting are pseudonymous per channel.** Subscribing to and pulling a channel reveals nothing to the publisher beyond a connecting Tor circuit (a private channel also requires the shared capability). Since 3.0.15 a reaction, comment, announcement or application is signed with a key derived for that channel from the member's identity private key: the publisher and every other subscriber see the same key for the same member in that channel, and the name the member chose to announce there, if any, but not the identity key the member's contacts know, and a member's keys in two channels cannot be linked without the identity private key. A member's activity within one channel is linkable to itself by design. Clients up to 3.0.14 still sign with the identity key and the account name. A publisher can also serve different content to different readers to tell them apart (next item).
- **Channel publishers can equivocate.** Because subscribers do not gossip with each other, a malicious publisher could serve a different post history to different subscribers (a fork). The signature chain guarantees that each subscriber's view is internally consistent and authentically signed by the publisher, but not that all subscribers see the same view. This is inherent to single-publisher broadcast without a shared consistency oracle. Expiring and deleted posts are deleted; since 3.0.15 the chain tip stays, so later posts still link, and a subscriber that never held a removed post bridges the gap under the publisher's signature ([docs/wire/CHANNELS_WIRE_PROTOCOL.md](wire/CHANNELS_WIRE_PROTOCOL.md), Hash chain).
- **The Bitcoin wallet uses a lightweight (Electrum) client, not full SPV.** Balances and confirmation counts are server assertions, checked against local structural and signature validation but not against proof-of-work. A malicious server cannot derive keys, sign, redirect a signed transaction, or make the wallet spend more than the reviewed plan (the signature commits every input and output); it can, however, withhold data or misreport confirmations, so a receiver should treat a single server's confirmation count with appropriate caution. Independent header/merkle verification is possible future work.
- **Monero balance reconciliation is view-based.** Because the runtime wallet is view-only, a spend made from the same seed in a different wallet is reconciled into the displayed balance the next time the wallet is opened with its password, not continuously. A Zerion send always opens the spend wallet first, so it can never select an already-spent output; the reconciliation concerns display, not fund safety.
- Endpoint compromise, Tor traffic-confirmation, and coercion are out of scope.

## 12. Cryptographic parameters

| Purpose | Primitive | Parameters |
|---|---|---|
| Key agreement | X25519 + ML-KEM-768 (hybrid) | ML-KEM enc key 1184 B, ciphertext 1088 B, decap key 2400 B, shared secret 32 B |
| Signatures | Ed25519 + ML-DSA-65 (hybrid) | ML-DSA public key 1952 B; hybrid signature 3373 B |
| AEAD | XSalsa20-Poly1305 | 24-byte nonce, 256-bit key, 128-bit tag |
| KDF / MAC | Keyed BLAKE2b | 256-bit output, domain-separated labels (`org.zerionproject/...`) |
| Message ratchet | Mode 3-Full | per-message ML-KEM-768; key-pair rotation every 16 own sends; up to 32 retained key pairs per connection |
| Root evolution (from 3.0.15) | X25519 + ML-KEM-768 (hybrid) | at the start of a connection, at most once per 10 min per contact; paused 7 days after a backup or transfer |
| Wire frame | ZWF | fixed 4096 B; 16-byte tag; 8-byte persistent stream id; replay window 256 |
| Transport pacing | ZPP | one frame per 750 ms (active) or 4 s (idle, on every network type) ±1/3 jitter, real-or-cover; idle after 2 min without application records |
| Voice | PCM + AES-256-GCM (see §8 for the 3.0.11 status) | 16 kHz mono 256 kbit/s, 20 ms / 640-byte frames |
| Account database key | Argon2id + keystore HMAC | 64 to 256 MiB adapted to the device (default 128 MiB), t=3, p=1; legacy scrypt files still open |
