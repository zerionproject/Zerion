# Mode 3-Full / ZWF / ZPP security-claims matrix

Each row is a claim about the **currently shipped** protocol, the production code
that enforces it, and the regression test that proves it. Claims not backed by
both a production invariant and a test are marked as such and either weakened or
listed as future work. Do not add proposed/future properties as current
guarantees.

## Compromise model (claim 3 / PCS scope)

Post-compromise security in Mode 3-Full rests on the per-message ML-KEM ratchet
within a connection and on root evolution across connections; there is no
classical DH ratchet. The one-way chain gives forward secrecy within a stream
against a copy of its current chain key. Against a later copy of the persisted contact root key,
forward secrecy comes from the ML-KEM layer: every application frame mixes a
secret encapsulated to a per-connection key pair that is zeroized once the peer
uses a newer one or the connection ends, so after the first ML-KEM secret the
chain cannot be rebuilt from the root. Only the opening cover frames can be,
and they carry no application data. A copy of the root together with a key pair
that is still held exposes the frames of the current connection that depend on
that key pair. The ML-KEM secrets also give post-quantum confidentiality, the
encapsulation to the peer's current key gives post-compromise security for this
side's outgoing frames (as long as the peer's decapsulation key is not
compromised), and rotating this side's own key pair gives it for its incoming
frames once the peer uses the new key. These healing statements assume the
attacker only observes after the copy. An attacker that also holds the stream
chain keys and injects frames can substitute the advertised keys and keep its
position until the connection ends; one that also holds the contact root key
can do so in later connections until a root evolution it does not take part in.
For each compromised state:

| Attacker copies | Zerion currently provides |
|---|---|
| Current symmetric stream chain key only | Forward secrecy for earlier messages; the compromised chain state exposes frames until the next ML-KEM secret is mixed in, after which the chain depends on a secret the attacker cannot decapsulate. |
| Active local ML-KEM private key | Our outgoing frames are not affected (they are encapsulated to the peer's key). With this key alone the attacker reads nothing (it also needs the receive chain key). If it also holds that, our incoming frames heal once the peer encapsulates to a key pair the attacker never saw (claim 3): on the same connection after we have sent or received 16 frames on it since our last rotation and the peer has received the new public key and used it; otherwise on the next connection, which starts with a new key pair (claim 4). An attacker who holds back our outgoing frames delays this until they get through, or until the peer has sent more than 128 frames in a row on one of our key pairs, when we close the connection (claim 1). Rotation pauses while 32 retired key pairs are retained (claim 1). |
| Complete current in-memory Mode 3-Full state (active + retained keys) | Heals on the same connection once the peer uses a key pair generated after the snapshot, which prunes and zeroizes every older one; otherwise on the next connection, whose state is new, provided the copier does not also hold the contact root key (next row) or only observes. The same conditions as the row above apply. |
| Persisted contact root key | Recorded earlier connections stay closed to the copy: every application frame mixes an ML-KEM secret for a per-connection key pair that has since been zeroized, so only their opening cover frames can be rebuilt. Heals at the next root evolution the attacker does not take part in (ZWF-ROOT-EVOLUTION.md): afterwards the copied root no longer authenticates in either direction. A holder of the copy who only reconnects and replays HELLO cannot stall the evolution or cut the legitimate device off. An attacker holding the current root and active during that evolution keeps its position, or displaces the legitimate peer, who is then shown that the keys are out of sync and re-adds the contact. No healing with a peer that does not support root evolution (Android 3.0.14, iOS), until the two re-pair. |
| Static identity material | Out of scope (identity, not session PCS). |

"Post-compromise recovery" is therefore **per-connection and ML-KEM-driven**:
within a connection a side's outgoing direction heals at its next frame that
carries an ML-KEM secret, and its incoming direction heals once the peer uses
the key pair it makes after 16 frames sent or received since its last rotation, and a connection whose peer stays on one key pair for more than 128 frames is closed; every new
connection starts with new key pairs; the contact root key
heals **at the next root evolution** across connections; it is not the classical "PCS after one
round-trip". Do not restate the one-round-trip claim.

## Label discipline for hybrid signatures

The Ed25519 half of a hybrid signature is the classical signature over the same
framed message, so a hybrid signature truncated to its classical half verifies
as a classical signature under the same label. Every hybrid label is therefore
distinct from every classical label (for example `EXCHANGE` against
`EXCHANGE_HYBRID`), and a new signature use must keep that rule: a label shared
between a classical and a hybrid use would let a hybrid signature stand in for a
classical one.

## Not current guarantees (future work)

- An independent, actively-ratcheting classical X25519 PCS layer within a
  connection (a cryptographic-design change, out of scope).
- Root evolution with peers that do not implement it (Android 3.0.14, iOS) and
  healing of a root an attacker copies while also being active during the
  next evolution.
