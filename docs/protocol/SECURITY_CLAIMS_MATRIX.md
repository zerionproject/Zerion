# Mode 3-Full / ZWF / ZPP security-claims matrix

Each row is a claim about the **currently shipped** protocol, the production code
that enforces it, and the regression test that proves it. Claims not backed by
both a production invariant and a test are marked as such and either weakened or
listed as future work. Do not add proposed/future properties as current
guarantees.

## Compromise model (claim 3 / PCS scope)

Post-compromise security in Mode 3-Full rests on the per-message ML-KEM ratchet
within a connection and on root evolution across connections; there is no
classical DH ratchet. For each compromised state:

| Attacker copies | Zerion currently provides |
|---|---|
| Current symmetric stream chain key only | Forward secrecy for earlier messages; the compromised chain state exposes messages until the next ML-KEM secret is mixed in, then future keys heal as rotation advances. |
| Active local ML-KEM private key | Heals on the next rotation to a key pair the attacker never saw, once the peer encapsulates to the new key (claim 3). Bounded by the rotation interval of our own sends. |
| Complete current in-memory Mode 3-Full state (active + retained keys) | Heals after enough rotations that all snapshotted key pairs are evicted from the retention LRU and a fresh key pair is in use. |
| Persisted contact root key | Heals at the next root evolution the attacker does not take part in (ZWF-ROOT-EVOLUTION.md): afterwards the copied root no longer authenticates in either direction. A holder of the copy who only reconnects and replays HELLO cannot stall the evolution or cut the legitimate device off. An attacker holding the current root and active during that evolution keeps its position, or displaces the legitimate peer, who is then shown that the keys are out of sync and re-adds the contact. No healing with a peer that does not support root evolution (Android 3.0.14, iOS), until the two re-pair. |
| Static identity material | Out of scope (identity, not session PCS). |

"Post-compromise recovery" is therefore **per-connection, ML-KEM-driven, bounded
by the own-send rotation interval** within a connection, and **at the next root
evolution** across connections; it is not the classical "PCS after one
round-trip". Do not restate the one-round-trip claim.

## Label discipline for hybrid signatures

The Ed25519 half of a hybrid signature is the classical signature over the same
framed message, so a hybrid signature truncated to its classical half verifies
as a classical signature under the same label. Every hybrid label is therefore
distinct from every classical label (for example `EXCHANGE` against
`EXCHANGE_HYBRID`), and a new signature use must keep that rule: a label shared
between a classical and a hybrid use would let a hybrid signature stand in for a
classical one.

## Not current guarantees (future work)

- An independent, actively-ratcheting classical X25519 PCS layer within a
  connection (a cryptographic-design change, out of scope).
- Root evolution with peers that do not implement it (Android 3.0.14, iOS) and
  healing of a root an attacker copies while also being active during the
  next evolution.
